# Discussion
- The images prepared beforehand have been shown to @iambusra.
- @iambusra explained some linguistic concepts and why some features offered would be useful or not.
- @iambusra has given feature ideas that would be useful to design for before the implementation actually takes place.
- Under the image **2**: @iambusra explained what it takes for a sentence to be considered _annotated_. The conditions are: Every lemma should have a head and every edge should have a _DEPREL_. Some features must be filled for a complete annotation but there are too many nuances to consider, especially for Turkish, and it's not to be implemented. The decision was to have a flag instead, where a flag can be _annotated_, _half-annotated_ or _null_ for a sentence. This should help the annotator to go back to the sentences half annotated, easily.
- Under the image **3**: The annotator has requested there to be a regular expression functionality.
- Under the image **5**:
    - The annotator has agreed to opt out of the previous tree representation and opted to use a linear tree, like the one below, taken from [here](https://spacy.io/displacy-compact-4c063e533e7ca1019a2f763ed5b7a925.svg).
        ![tree](uploads/2cfc27396fe4bafa93fbb070892b898d/tree.png)
        It is agreed to be more compact and takes much less time to understand the tree relations on. The lemma indices can be written to this graph as well (making the top-most sentence representation redundant) and this graph should be refreshed dynamically to show new relations annotated.
    - The errors are thought to be better represented on the feature table with exclamation points and colors.
- Errors: The user should be able to flag some errors _seen_, where an annotator decides to annotate a part that's invalid by the application and flags the error _seen_. The thinking behind was that if there were a part that were showing error but many annotators agreed on it, this could be a case for a proposal of change for the format of annotation of sentences.
